# Images and boot validation

The appliance uses an Alpine Linux kernel and a custom initramfs. `/init` is a
symlink to the static `routerd` binary. The root filesystem contains the
`routerd` and `routerd-modules` executables, configuration, CA certificates,
license text, and Linux modules. It contains no shell, OpenRC, systemd, apk,
modprobe, or decompression programs. PID 1 mounts the virtual filesystems and
uses routerd's native kernel module loader. Worker processes execute the
`routerd-modules` binary under the supervisor.

Alpine's package tools are build dependencies. `packaging/alpine/Dockerfile`
runs the test suite through `abuild`, builds the routerd APK, and installs that
APK into a staging root. A separate image stage installs `linux-virt`, extracts
the required files, decompresses the kernel modules, and regenerates
`modules.dep`. The build publishes its kernel release and input package hash in
`manifest.json`. Kernel provenance also includes the exact Alpine package
version and the pinned aports commit/recipe URL. The manifest explicitly records
that this development image does not bundle a corresponding kernel-source
archive; the Go dependency notice collection does not satisfy that separate
release-distribution task.

For development inside an Alpine image-builder environment,
`scripts/build-image.sh --binary-dir DIR --output DIR` accepts the two existing
binaries directly and requires `dist/licenses`, generated by `make licenses`.
Its manifest says `input_type: development-binaries` and
contains no package hash. This is useful for rapid boot debugging and does not
replace the APK build/test gate used by `make image` and CI.

## Build an appliance

Requirements: Docker with BuildKit. QEMU and Python 3 are needed only for the
smoke test.

```sh
make apk
make image
make qemu-smoke
```

Artifacts are `dist/image/vmlinuz`, `initramfs.cpio.gz`, `manifest.json`, and
`SHA256SUMS`. The default image has empty network configuration and SSH disabled.
It does not configure the build host or expose an unauthenticated management
service.

`linux-virt` is a VM-oriented kernel. This initial image is validated on QEMU
x86_64 using virtio networking. Native amd64 and arm64 routerd binaries and OCI
images are built separately; the arm64 appliance boot path and physical NIC
drivers are not yet validated.

## QEMU fixture with the embedded SSH CLI

The QEMU fixture assigns `10.0.2.15/24` to `eth0` and uses QEMU's user-mode
gateway `10.0.2.2`. Generate a disposable key and inject only its public half:

```sh
ssh-keygen -q -t ed25519 -N '' -C routerd2-qemu -f /tmp/routerd2-qemu
export SSH_AUTHORIZED_KEY="$(cat /tmp/routerd2-qemu.pub)"
make image IMAGE_CONFIG=qemu
make qemu-smoke QEMU_SSH_KEY=/tmp/routerd2-qemu
```

The test uses TCG so it also works without KVM. It waits for `ROUTERD_READY`,
fails on a kernel panic or early exit, then runs `show status`, `show network`,
`show config`, and `show version` through the embedded SSH server. It verifies
PID 1, release identities, the configured IPv4 address, and recovery of the
committed network revision after restarting its worker. Its random
loopback-only forwarded port and temporary known-hosts file do not change host
SSH settings. Serial output is retained as `dist/image/qemu-serial.log`.

The generated fixture contains the test public key and fixed test addressing.
Do not deploy it as a production configuration. The private key is never copied
into an image or uploaded as a CI artifact.

## Native kernel packet tests

```sh
make qemu-network
```

This boots a separate test-only initramfs with the same kernel and module tree.
It attaches **no virtual NIC** to the VM. The integration test creates fresh
user and network namespaces inside the guest, then exchanges real packets:

- IPv4/IPv6 forwarding, NAT44/NAT66, source-policy routing and weighted ECMP
  across both next-hop interfaces.
- INPUT/OUTPUT/FORWARD ACLs with family, source/destination prefixes,
  interfaces, TCP/UDP port ranges, DROP and on-wire ICMP REJECT responses.
- DNAT plus SNAT, translated TCP/UDP port ranges, masquerade ranges,
  NAT-only hooks, and existing connection survival across atomic replacements.
- A symmetric IPv4-in-IPv6 DS-Lite tunnel with a B4 point-to-point peer.
- Bridge forwarding, VLAN/VRF/VXLAN/macvlan create/update/removal, explicit
  IPv6 address lifetimes and deprecation, and foreign-child preservation.
- RA/SLAAC kernel writer settings applied before interface activation, exact
  restoration of their prior values, and finite IPv6 routes that expire in
  the kernel even when no reconciliation runs. Renewal and weighted ECMP
  route expiry are covered as well.
- VRRP virtual MAC/NoDAD configuration and Accept_Mode=false VIP guards,
  including ND/VRRP exceptions and unaffected forwarded traffic.

It also checks that reverse new connections are dropped, unrelated kernel state
survives, and owned state is removed/restored. A namespace failure is a test
failure, never a passing skip. `dist/network-test` retains the serial log,
result manifest and test initramfs. The test initializer and test binary are
not included in the production appliance or OCI image.

`make qemu-daemon` uses the same initializer and archive builder, with a fixed
`daemon` suite. It freshly builds both commands and the integration test
executable, puts the commands at `/test/bin` inside a guest with no external
NIC, and requires `TestDaemonRAClientConfigurationAndExpiry` to report PASS.
The suite checks RA configuration and expiry through the real supervised
process tree. `dist/daemon-test` records the selected test, all executable
hashes, the kernel hash and the serial log. Renamed tests, missing tests and
skipped tests fail the gate.

`make qemu-daemon-aftr` selects the fixed `daemon-aftr` suite and requires
`TestDaemonAFTRResolutionAndExpiry`. It uses the same binary build and guest
isolation path; its independent artifacts are under `dist/aftr-daemon-test`.

`make qemu-ra-dns` requires `TestIsolatedLearnedDNSLifetimes`. Actual RA packets
must show static DNS precedence, learned RDNSS/DNSSL countdown, live renewal and
removal, expiry after the update stream closes, and shutdown withdrawal. The
worker keeps the same process while its configuration generation changes.
Artifacts are under `dist/ra-dns-test`.

`make qemu-wireguard` selects the fixed native WireGuard suite. It verifies
IPv4/IPv6 encrypted TCP over both UDP address families, kernel handshake/counters,
authenticated endpoint roaming, a 2050-prefix multipart peer update, a real
partial-set interruption with restart rollback, wrong-PSK and peer-removal
rejection, foreign-peer preservation and cleanup. It uses the same no-NIC guest
builder and records independent artifacts under
`dist/wireguard-test`.

## Protocol and process integration gates

```sh
make qemu-protocols
```

This target runs eight fixed suites in separate no-NIC guests, using the same
Alpine kernel and module tree as the appliance. CI runs these packet and
namespace checks in the `images` job: a hosted runner's kernel may omit VRF or
other drivers even when it provides root access. The host `go` job still runs
formatting, unit tests, race detection, vet, both static architecture builds,
and actual signed-bundle validation.

| Suite | Required test | What it verifies |
| --- | --- | --- |
| `daemon-management` | `TestDaemonConfigurationAndRecovery` | Embedded SSH editing, commit and process recovery |
| `daemon-dhcp-dns` | `TestDaemonDHCPDNSAndOwnershipExpiry` | DHCP leases projected into DNS and ownership expiry |
| `daemon-bgp` | `TestDaemonBGPFIBAndOwnershipExpiry` | Real BGP workers, kernel FIB and ownership expiry |
| `dhcp` | `TestIsolatedNativeDHCPAndRA` | DHCPv4, DHCPv6-PD and native router advertisements |
| `dhcp-server` | `TestIsolatedNativeDHCPServer` | DHCP server VRF binding, lease lifecycle and restart |
| `vrrp` | `TestIsolatedNativeVRRP` | IPv4/IPv6 VRRP elections and failover |
| `ra-client` | `TestIsolatedNativeRAClient` | RA learning, independent lifetimes, DAD and restart |
| `aftr` | `TestIsolatedNativeAFTR` | AFTR resolution over native IPv6 DNS transport |

The three `daemon-*` suites each build and execute the actual `routerd` and
`routerd-modules` pair. Every suite still uses fresh namespaces inside its
guest. Missing drivers, namespace failures, skipped tests, renamed or missing
test functions, incorrect PASS markers and nonzero QEMU exits fail the gate.
Required DHCP server validation also requires its VRF path; it cannot fall back
silently to an ordinary interface.

Each suite writes its serial log, test image and hash manifest under
`dist/<suite>-test/`. To run a single fixed suite, use
`python3 scripts/qemu-network.py --suite <suite> --image-dir dist/image`.
These fixtures add no programs or test commands to the production userland.

## Signed release validation

After `make build-linux RELEASE_ID=<id>`, run
`make release-built-test RELEASE_ID=<id>`. The required integration test inspects
both actual amd64 and arm64 executable pairs, builds signed bundles and stages
them through the release store. It verifies ELF identity without executing the
incoming payload. This gate does not itself boot either architecture.

`make qemu-release-boot` runs the release-boot package's dedicated fixture using
the same source image kernel/module artifacts. It freshly builds baseline and
trial binary pairs, then exercises signed selection and confirmation while the
selected routerd is actual guest PID 1. The independent witness records the
trial release identity, pinned executable verification, supervisor generation,
configuration revision and four worker names. The runner requires its exact
PASS marker, witness and a clean guest poweroff with QEMU exit zero. It writes
logs, hashes and the manifest to `dist/release-boot-test`.

This PID 1 fixture demonstrates selection and confirmation. It does not certify
bootloader A/B recovery across two physical boots or provision persistent media.

## Dependency notices

`make licenses` collects original license, notice, copyright and patent files
from the complete selected Go module graph and the Go toolchain. Missing module
root license files fail the build. `dist/licenses/manifest.json` records exact
module versions, module sums, notice hashes and the `go.mod` hash. It separately
lists packages imported by the static amd64 and arm64 command builds, so the
complete build graph is not mistaken for runtime linkage. This collection does
not infer SPDX license identities or assert compatibility. The image's Linux
kernel and any future packaged external engines need their own source and
license distribution records; they are outside this Go dependency inventory.

The local `third_party/google-nftables` replacement preserves v0.3.0 source
notices and records the original version, commit, archive checksum and the
narrow masquerade port-range fix. The license manifest records its actual
local source digest separately from its upstream module checksum. The library
regression runs in `make check` and the APK check phase; QEMU additionally
checks that the translated source ports fall inside the configured ranges.

## Container profile

```sh
make container
make container-smoke
make container-multi
```

The final OCI stage is `scratch` and explicitly starts `routerd run --platform
container`. It contains both executables and CA certificates, with no Alpine
userspace. Both runtime profiles include the project's license and the collected
dependency notices under `/usr/share/licenses/routerd2/`. The smoke test creates
an isolated network namespace, grants
`NET_ADMIN` and `NET_RAW`, uses a read-only root with writable runtime/state
tmpfs mounts, queries the control API, and checks graceful shutdown.

The container does not boot a kernel. The host must provide the required Linux
network features and kernel modules. This repository does not install a CNI,
join a Kubernetes cluster, replace kube-proxy, or claim an operational SDN
deployment simply by building this OCI image.

## Current persistence and boot limits

This image boots directly with a kernel plus initramfs. The default boot document
has no state volume, so its state directory is in RAM and generated SSH host keys
and other state are lost on reboot. A custom boot document can select an existing
ext4 block device with [`state_volume`](../internal/runtimeconfig/README.md).
The real PID 1 loads the configured storage drivers, mounts and verifies that
device before opening state, and refuses startup if the volume cannot be used.
The builder neither provisions nor formats the device.

The manifest distinguishes `volatile-initramfs` from
`configured-ext4-state-volume`, records the declared volume and boot-document
digest, and explicitly says it did not provision that volume. A declaration
does not prove the device was attached or successfully mounted. The independent
[two-boot storage gate](storage-test/README.md) verifies persisted configuration,
SSH keys and fallback between signed userland generations. Configured signed
userland selection includes trial/health confirmation and rollback; it is not
a bootloader or kernel/rootfs A/B update.

No disk image, installer ISO, cloud image or cloud-provider integration is
produced. Firmware-specific boot, Secure Boot enrollment, bootloader slot
selection and physical power-loss guarantees remain outside this builder.
`bootloader_ab_updates` remains false for both state-volume profiles.

Alpine and Go patch versions are pinned in the build arguments. The kernel
package is resolved from the pinned Alpine release branch and its exact version
is recorded; fully frozen package mirrors and base-image digests are a later
reproducible-release step.
